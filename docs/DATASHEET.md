# Datasheet: BBO Capstone Dataset

## Motivation

**For what purpose was the dataset created?**
The dataset records a 13-week black-box optimisation (BBO) challenge. The task was to find the input that maximises each of eight unknown functions, using only one new evaluation per function per week. It contains every point I evaluated and was used to train the surrogate models that chose each next query.

**Who created the dataset, and on whose behalf? Who funded it?**
The eight functions and the starting points were created by the course team for the Professional Certificate in Machine Learning and Artificial Intelligence at Imperial College Business School. The weekly queries were chosen by me, Chakkapas Visavakul, and evaluated by the course's capstone project portal. The dataset received no separate funding; it was produced as part of the course.

## Composition

**What do the instances represent?**
Each instance is one evaluation of a function: an input vector with 2 to 8 values, each between 0 and 1, and the single output the function returned. The functions are synthetic. They don't describe people or real-world measurements.

**How many instances are there?**
279 in total: 175 starting points supplied by the course and 104 weekly queries (8 functions × 13 weeks, Weeks 12–24).

**Is there any missing data?**
No. Every submitted query has a returned output.

**Does the dataset contain confidential data?**
No. It contains only numbers generated by synthetic functions, with no personal or confidential information.

## Collection process

**How was the data acquired?**
- **Starting points:** supplied by the course as NumPy files (`initial_inputs.npy`, `initial_outputs.npy`) for each function.
- **Weekly queries:** each week I ran my optimisation scripts on all the data collected so far, submitted one input per function through the capstone portal (rounded to six decimal places), and received the outputs. The portal provides cumulative files, which I saved as `inputs.txt` and `outputs.txt`, one line per week.

**If the data is a sample of a larger set, what was the sampling strategy?**
How the course chose the starting points isn't documented; they appear to be spread across the input space. The weekly queries are **not** a random sample. Each was chosen deliberately by an optimiser:

- Week 12: experiments, including points chosen to fill the largest empty regions.
- Weeks 13–19: GP with Expected Improvement or Lower Confidence Bound, starting exploratory.
- Weeks 20–22: TuRBO and HEBO.
- Weeks 23–24: a local search within a small box around the best point.

The per-week method and settings are recorded in `src/week-run-params.csv`.

**Over what time frame was the data collected?**
13 weekly rounds, from Module 12 to Module 24 of the course (2026).

## Preprocessing/cleaning/labelling

**Was any preprocessing done?**
- `src/dataset_csv.py` combines the starting files and the weekly files into one table per function (`data/funcN-data.csv`, with columns `X0…Xd−1, Output`). The values themselves are unchanged.
- Inputs were clipped to [0, 1] and rounded to six decimals before submission, as the portal requires. The upper bound is in practice 0.999999.
- Some transformations happen only inside the models and aren't saved as data: outputs are standardised before fitting the GP; Function 5 is modelled as log(y); and outputs are negated where a library minimises rather than maximises (`scikit-optimize`).
- No data points were removed or relabelled.

**Was the raw data saved?**
Yes. The original `.npy` files and the portal's `inputs.txt` and `outputs.txt` are kept unchanged in `data/`, so the CSV files can be regenerated at any time.

## Uses

**What other tasks could the dataset be used for?**
- Benchmarking other BBO methods or acquisition functions under a very small evaluation budget.
- Testing surrogate models on small datasets, for example comparing GPs, tree models or neural networks.
- Studying the exploration–exploitation trade-off: the record shows which strategy was used each week and what it achieved.
- Teaching, for example plotting how optimisation progress develops over time.

**Is there anything about the composition or collection that might affect future uses?**
- **Biased sampling:** the weekly points are concentrated near the best regions I found, especially in Weeks 23–24, so a model trained on them will be most accurate there and least reliable elsewhere. The data does not represent the whole input space.
- **Noise:** in Week 21 a script error resubmitted Week 20's inputs. For identical inputs, Function 2 returned 0.569 and then 0.611, and Function 3 returned −0.095 and then −0.103. These functions are noisy, and small differences between their outputs may not be real. I didn't test the other functions for noise.
- **Extreme scales:** Almost all of Function 1's outputs are tiny numbers, positive or negative, with magnitudes from about 10⁻¹⁶⁴ to 10⁻¹⁶. Only a handful are meaningfully different from zero. Function 5's outputs reach thousands. Models need suitable transformations, such as logs, to handle either.
- **Small size:** 23–53 points per function in 2–8 dimensions covers the space very thinly.

The data contains no information about people, so there is no risk of unfair treatment of individuals or groups.

**Are there tasks for which the dataset should not be used?**
It shouldn't be used to draw conclusions about real-world systems. The functions are synthetic, and their real-world names (such as "drug discovery") are only illustrations. It also shouldn't be treated as an unbiased sample for estimating each function's overall shape.
